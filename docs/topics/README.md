## 一頁摘要

兩題都套得進同一個四層結構，換的是資料與「情境」怎麼算：

| 層 | #4 塞車（已完成） | 車禍 | 公車設點 |
| --- | --- | --- | --- |
| 1. 熱力圖 | 入口 × 15 分鐘，車速 | 路口 × 時段，傷亡事故件數 | 里 × 指標（覆蓋率、高齡人口、步行分鐘） |
| 2. 幫你決定 | 幾點經過入口 | 你常經過的路口要注意什麼；繞路值不值得 | 多走幾分鐘到哪一站，等車最短 |
| 3. 如果大家都這樣 | 大家擠同一個時段 → 新尖峰 | 大家都繞同一條路 → 那條路變危險 | 每個人都要一站在家門口 → 公車變慢 |
| 4. 城市行動 | 彈性上班、幼托、接駁 | 依「事故 × 回報 × 缺少的設施」排路口改善 | 依「新增覆蓋人數 × 高齡比例」排設站與候車亭 |
| 情境滑桿 | 移出尖峰的比例 → 排隊 | 改善前 N 個路口 → 少幾件（或：事故排除時間 → 排隊） | 新設 N 站 → 覆蓋率、每班公車多花的時間 |
| 一頁紙給誰 | 市府與企業 | 交通局、交工處、警察局 | 公運處 |
| 真實資料 | VD（已收 4 天） | 傷亡事故逐案資料（有經緯度，10/23 下載得到） | 公車站牌座標、里人口（10/23 下載得到） |
| 現有設計稿 | `Main`、`V2*` | `A2*`（機車）、`A4*`（行人） | `A3*`（最後一哩路） |

**最大的差別：** 兩題的真實資料都是下載就有的靜態資料，不像 #4 要自己收；但兩題的情境都不是排隊模型，現在的資料契約裝不下（見下面「契約要補的地方」#6）。

## 先決定的事（今晚或 T0 前，10 分鐘）

1. **車禍題主做 A 還是 B？** 建議：題目講傷亡就做 A；講內湖交通就做 B，A 只放一張熱力圖。
2. **公車題主打「站點覆蓋」還是「候車亭」？** 建議：覆蓋當主體，候車亭當城市行動的一項；題目明講遮蔽、等車環境時才反過來。
3. **網站接不接「非排隊的情境」（#6）？** 不接的話：車禍只能做 B；公車題的情境改成固定的「前 10 站清單」加一張覆蓋率曲線圖。

## 契約要補的地方（提案，待網站工程師確認）

依契約規則只新增欄位、不改名。編號接在 [`data/mock/README.md`](../../data/mock/README.md#演練找到的契約問題待網站工程師確認) 的 #1–#5 之後。

| # | 問題 | 提案 |
| --- | --- | --- |
| 6 | `scenario` 只裝得下排隊模型（`capacity`、`baseline`、`results` 必填，結果要有排隊長度與消散時間）。車禍 A 的「改善前 N 個路口」、公車的「新設 N 站」是「滑桿值 → 幾條結果曲線」 | 新增選填 `scenario.curve`：`x`（滑桿刻度陣列）、`series[]`（`id`、`name`、`unit`、`values[]`、`lo[]`、`hi[]`、`label`、`sim`）、`marks[]`（例如「效益開始變小」的那一點）。有 `curve` 時 `capacity`、`baseline`、`results` 改選填；網站畫折線，滑桿讀同一個刻度的值 |
| 7 | 認領後端存「日期、入口、時段、匿名代碼」，有名額。車禍的「差點出事」、公車的「這裡需要一站」是回報，沒有名額 | 後端多一種回報：存「日期、地點 id、類別、匿名代碼」，同一裝置每天每地點每類別只算一次，不設名額。城市頁照樣只顯示彙總，JSON 裡的人數照樣 `pending` |
| 8 | 地點太多：路口可能上千個，臺北市約 450 個里，熱力圖排不下 | 熱力圖只放排序後的前 20 列；全部地點放新增的選填 `heatmap.points`（id、名稱、座標、主指標值）給地圖用，地圖用點上色 |
| 9 | `city.goal` 的說明寫的是「要移出幾 %」 | 文字本來就從 JSON 讀，只要網站不寫死「移出」兩個字 |

#7、#8 不做也能交：回報先只存在手機，熱力圖只放前 20。#6 不做的話影響最大。

## 隱私（兩題共通）

- 事故逐案資料有時間、地點、年齡、性別，組起來可能認出當事人（死亡事故常有新聞）。**只顯示彙總到路口的件數，不畫單筆事故的點，不在路口層級分年齡、性別**；件數少於 3 的格子顯示「少於 3 件」。
- 回報只記到路口或候選站點，不記 GPS 座標；照片選填，提醒避開人臉與車牌（同設計稿 `A4App`）。
- 陳情資料照舊只放彙總，原文不進 repo。
